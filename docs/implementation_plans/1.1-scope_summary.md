## 1. What the v4 Plan Proposes Across All 6 Phases

### Phase 0 — Project Skeleton + Pre-flight (~30 min build)
Sets up `pyproject.toml`, `config.py`, `models.py`, `docker-compose.yml`, `scripts/validate_env.py`, `scripts/run_pipeline.py`, and all `__init__.py` stubs. Defines the **complete Pydantic data contracts** that every later phase imports. Smoke test: `pip install -e .` succeeds; `from blast_radius.config import settings` loads.

### Phase 1 — Playwright Crawler (~2–4 h build, ~5–10 min run)
Two sub-modules:
- `dynamic.py` — Playwright-based crawl of `app.documenso.com`, both unauthenticated (marketing, signup, login) and **authenticated** (document list, template list, signing flows). Captures DOM snapshot, accessibility tree, screenshots, page transitions. Outputs `PageSnapshot` + `CrawlManifest` to `data/crawl/`.
- `static.py` — `httpx` fetch of `docs.documenso.com` (first 5 pages). Outputs as additional `PageSnapshot`s.

Smoke test: ≥2 JSON files in `data/crawl/`.

### Phase 2 — Docling + LLM Ingest (~2–3 h build, ~2–5 min run)
- Fetches `README.md` (via `httpx`, not Docling URL) + `docs.documenso.com` pages (capped at 3 pages).
- Passes text to `call_llm_json()` with a prompt specifically tuned to explicitly hunt for **implicit requirements** — features/capabilities mentioned in docs that are not framed as explicit user stories (these are key `GapNode` absence candidates).
- Deduplicates. Outputs `data/requirements/requirements.json` (list of `Requirement`).

Smoke test: ≥10 requirements; ≥3 have `related_ui_keywords`; explicit + implicit requirements present.

### Phase 3 — ast-grep + GitHub API Code Index (~2–3 h build, ~3–8 min run)
- `index.py` runs `sg --json` with `rules/ts-functions.yml` + `rules/trpc-procedures.yml` over `data/repos/documenso`. Builds `CodeFunction` list with file/line/name/calls.
- `pr.py` calls GitHub API via `httpx` to fetch PR file list + diffs → `PRDelta` model. **No PyDriller** (replaced as required).
- Outputs `data/code/call_graph.json` + `data/code/pr_{number}.json`.

Smoke test: ≥50 functions; PRDelta has ≥1 changed file.

### Phase 4 — Entity Resolution + Neo4j Graph Build (~3–4 h build, ~5–15 min run)
Three-step build:
1. `schema.py` — creates Neo4j constraints and indexes.
2. `writer.py` — MERGEs `Requirement`, `UIElement` (from crawl pages), `CodeFunction` nodes. Writes `CALLS`, `RENDERS`, `IMPLEMENTS` edges.
3. `resolve.py` — entity resolution: keyword pre-filter → cosine similarity (sentence-transformers, threshold 0.60) → `call_llm_json()` reranker → `IMPLEMENTS` edges. Marks absent requirements as `GapNode`s.

Smoke test: ≥1 `IMPLEMENTS` edge; ≥1 `GapNode` (unless all requirements covered).

### Phase 5 — PR Blast Radius (PPR + DFS) (~2 h build, ~1–3 min run)
- Loads graph from Neo4j into NetworkX.
- Seeds PPR at changed `CodeFunction` IDs (matched via path alignment).
- Runs `networkx.pagerank()` with personalization. Applies 2.5× multiplier to sink nodes.
- DFS fallback: functions with code-descendants but no UI/req path → `dark_changes`.
- Outputs `BlastRadiusReport` JSON to `data/reports/`.

Smoke test: Report JSON non-empty; evidence paths are human-readable labels.

### Phase 6 — Jinja2 HTML + Markdown Report (~1 h build, <30 s run)
- `render.py` reads `BlastRadiusReport` JSON.
- Generates HTML via `templates/report.html.j2` (Jinja2, `autoescape=True`).
- Generates Markdown with executive summary (via `call_llm()`), HIGH/MEDIUM/LOW tiers, absent requirements, dark changes, coverage stats table.

Smoke test: Both files non-empty; no raw SHA hashes in evidence paths.

## 2. The 3 Highest-Risk Audit Findings

> [!CAUTION]
> These three bugs are silent — they produce plausible-looking but completely wrong output.

### 🔴 Risk #1 — BUG-04: `fn.file` vs `cf.path` format mismatch → 100% dark changes
**Phase:** 5 (path matching before PPR seeding)  
**Why it's the worst:** The report renders without crashing. All changed functions silently land in `dark_changes` regardless of actual graph coverage. The reviewer reads a technically valid but factually hollow report. An entire pipeline run produces zero actionable findings.  
**Fix (audit-guard BUG-04):** `verify_path_alignment(functions, delta)` — raise `ValueError` if zero paths match before Phase 5 runs.

### 🔴 Risk #2 — BUG-05: Auth credentials mandatory, not optional (Phase 1 → Phase 4 chain)
**Phase:** 1 (crawl), 4 (RENDERS assertion)  
**Why it's the worst:** Without auth, the only crawled pages are `/signin` and `/signup`. Their `UIElement` nodes match zero `CodeFunction` files. Phase 4's RENDERS assertion originally hard-fails. Even after downgrading to a warning, the entire UI layer of the graph is empty — affected UI = 0, making the report meaningless to a QA lead.  
**Fix (audit-guard BUG-05):** Validate `DOCUMENSO_EMAIL` + `DOCUMENSO_PASSWORD` in `validate_env.py` and raise a clear error at Phase 1 startup, not deep in Phase 4.

### 🔴 Risk #3 — BUG-07: GapNode accumulation across re-runs (Phase 4 idempotency)
**Phase:** 4 (graph build)  
**Why it's high-risk:** Every re-run of Phase 4 doubles the GapNode count. The "Absent Requirements" section of the report then lists each requirement 2×, 3×, N× times. The report is unreadable after the second run and the graph state is corrupted.  
**Fix (audit-guard BUG-07):** Two Cypher DELETE/RESET statements at the **start** of `build_graph()` before any MERGE.

## 3. Recommended 2-Phase Deep Investment

> [!IMPORTANT]
> Quality over coverage. Two solid phases beats six shallow ones. This is the assignment's own instruction.

### **Phase 2 (Ingest) + Phase 3 (Code Index)** — go deep here

**Why Phase 2 is the quality anchor:**
- Requirements are the foundation. Every downstream signal — PPR scores, absent-requirement findings, evidence paths — is only as good as the requirement nodes. Shallow Phase 2 = a graph that technically runs but produces findings nobody believes.
- The LLM extraction prompt must be tuned: correct req_type classification, meaningful `related_ui_keywords`, accurate provenance. This is where the assignment's "agent decomposition" and "confidence handling" design doc sections come to life with real examples.
- The `call_llm_json()` path is exercised here first — a good Phase 2 proves the LLM wrapper works end-to-end.

**Why Phase 3 is the technical credibility anchor:**
- The ast-grep rules (`ts-functions.yml`, `trpc-procedures.yml`) must correctly extract TypeScript functions from a real Turborepo monorepo. Getting this right means the call graph is real, not approximated.
- The `verify_path_alignment()` guard (BUG-04 fix) lives here conceptually and must be validated against real PR data.
- A correct `PRDelta` (via GitHub API, not PyDriller) with real changed-file paths is what makes the blast radius non-trivial.

**Phase 4 and 5 follow naturally** from a solid 2+3. Phase 1 (crawl) is needed for UIElement nodes but depth there is a secondary concern — a working auth crawl with 5–10 real document-lifecycle pages is sufficient.

## 4. Explicit Cuts (with One-Sentence Defence per Cut)

| Cut | What's cut | Defence |
|-----|-----------|---------|
| **Static doc crawl depth** | Cap `docs.documenso.com` to 3 pages, not 5 | Three pages (overview, features, API) yield enough diversity of requirements; page 4–5 are changelog/blog with near-zero unique requirement density. |
| **Call graph depth** | Only direct calls within Phase 3 files; no transitive cross-file call graph | The PR diff targets specific routers and lib functions; transitive closure adds noise from deeply shared utilities (Prisma client, logging) with near-zero discriminatory value for PPR seeding. |
| **O(N²) call detection fix** | Cache `file_content` per file (trivial fix) but do NOT rewrite to full tree-sitter AST call resolution | A text-regex call detector with file caching is fast enough for the ~500 functions in the target directories; a full CPG (Joern) is out of scope and would take more time than Phase 3's entire budget. |
| **ACI / ambiguity investigation loop** | No OpenHands / SWE-agent sub-agent | The assignment allows "when does the system stop and ask a human?" — the answer is the `manual_review_items` list in the report; an interactive ACI loop is a week-two feature. |
| **GNNExplainer / gradient attribution** | No GNN explainability | PPR + DFS evidence paths with human-readable labels already satisfy the "explainability" requirement for a non-engineer QA report; GNNExplainer adds ML overhead with no visible output improvement. |
| **unauthenticated crawl breadth** | Crawl only `/`, `/signin`, `/signup` without auth (≤3 pages) | These pages produce trivial UIElement nodes; all meaningful nodes come from the authenticated flow — investing crawl time in marketing pages is wasted. |
| **Markdown-only report** | Ship Markdown as primary; HTML as secondary | Markdown is grep-able, diffable, and directly readable by a QA lead in GitHub; HTML adds visual polish but zero semantic value for the assessment. |
