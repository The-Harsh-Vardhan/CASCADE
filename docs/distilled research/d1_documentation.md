# 1. Executive Summary

## Overview

Modern software systems evolve rapidly through frequent code changes, making it increasingly difficult for engineering and QA teams to understand the downstream impact of every Pull Request (PR). While source code repositories reveal *what* changed, they rarely explain *which product features, user interfaces, and business requirements are affected*.

Blast Radius Analyzer is an AI-powered impact analysis platform that bridges this gap by constructing an **Evidence-backed Product Knowledge Graph** connecting three layers of software knowledge:

- **Requirements Layer** — Product intent captured from PRDs, documentation, and specifications.
- **Experience Layer** — User-facing pages, UI components, and interaction flows discovered through autonomous application crawling.
- **Implementation Layer** — Source code, APIs, and data access patterns extracted from the application's repository.

Whenever a new Pull Request is opened, the system analyzes the code changes, retrieves the relevant portion of the knowledge graph, and generates an explainable **Blast Radius Report** highlighting:

- Product requirements potentially affected
- User interfaces at risk
- User journeys impacted
- Backend services involved
- Confidence of each inferred relationship
- Supporting evidence for every conclusion

The generated report is designed for both software engineers and QA teams, enabling earlier risk assessment, targeted regression testing, and improved release confidence.

---

# 2. Problem Statement

Understanding the impact of code changes remains one of the most time-consuming and error-prone activities during software development.

Traditional impact analysis techniques rely primarily on static code dependencies or developer intuition. While these approaches identify which files or functions have changed, they fail to answer higher-level product questions such as:

- Which user-facing features are affected?
- Which business requirements may lose coverage?
- Which regression test suites should be executed?
- Which product owners or QA engineers should review the change?
- How confident is the system in these conclusions?

As modern applications continue to grow in complexity, maintaining traceability between product requirements, user interfaces, and implementation becomes increasingly difficult.

Blast Radius Analyzer addresses this problem by continuously constructing a semantic representation of the product and leveraging it to perform explainable, evidence-backed impact analysis whenever source code changes occur.

---

# 3. Product Vision

Enable engineering organizations to understand the **product-level impact** of every code change before it reaches production by connecting software requirements, user experience, and implementation into a unified knowledge graph.

Rather than answering only **"What code changed?"**, the platform should answer:

> **"What product behavior is at risk, why do we believe that, and how confident are we?"**

# 4.3 Design Principles

The following principles guide every architectural and product decision.

## Explainability by Design

Every node, relationship, and conclusion should be traceable to supporting evidence.

The system must never produce conclusions without exposing the reasoning path that led to them.

---

## Retrieval Before Reasoning

Large Language Models should operate only on a carefully retrieved subgraph rather than the entire product graph.

Graph retrieval narrows the reasoning context, improves explainability, and reduces hallucinations.

---

## Human-in-the-Loop

Low-confidence mappings should be surfaced for review instead of being treated as facts.

Confidence is a first-class concept throughout the system.

---

## Language Independence

The knowledge graph should model software concepts independently of programming languages or frameworks.

A Function, Method, or Class should all be represented through a common abstraction where appropriate.

---

## Incremental Knowledge

Knowledge should evolve incrementally as the application changes rather than requiring complete graph reconstruction after every update.

---

## Evidence-Backed Relationships

Relationships should never exist without evidence.

Every edge in the graph stores:

- Confidence
- Evidence
- Source
- Last Verification Timestamp

This enables transparent reasoning and future re-validation.

The MVP focuses on delivering an end-to-end proof of concept capable of constructing a semantic product representation and performing explainable blast radius analysis for real Pull Requests.

The following capabilities are included in the MVP.

---

### S-001 Autonomous Application Crawling

The system shall autonomously explore a running web application and capture:

- Reachable pages
- Interactive UI components
- Navigation relationships
- User interaction transitions
- DOM metadata
- Screenshots

The crawler should operate without manually scripted page definitions.

---

### S-002 Product Documentation Ingestion

The system shall ingest product documentation from supported sources including:

- Markdown
- README files
- Product Requirement Documents (PRDs)
- Feature documentation
- GitHub Wiki pages

The extracted information should be transformed into structured product requirements.

---

### S-003 Repository Analysis

The system shall analyze a public source code repository and extract implementation artifacts including:

- Source files
- Classes
- Functions
- API endpoints
- Call relationships

---

### S-004 Knowledge Graph Construction

The system shall construct an Evidence-backed Product Knowledge Graph connecting:

- Product Requirements
- User Experience Layer
- Implementation Layer

Each relationship shall include supporting metadata required for explainable reasoning.

---

### S-005 Pull Request Analysis

The system shall analyze a Pull Request by:

- Parsing the code diff
- Identifying changed implementation entities
- Retrieving the relevant product subgraph
- Performing impact analysis

---

### S-006 Blast Radius Report Generation

The system shall generate a human-readable report containing:

- Executive Summary
- Changed Components
- Affected Requirements
- Affected Pages
- Affected User Flows
- Risk Assessment
- Supporting Evidence
- Confidence Scores
- Recommended Regression Areas

---

### S-007 Explainable Reasoning

Every reported finding shall include:

- Supporting graph path
- Evidence source
- Confidence score
- Explanation of inference

No conclusion should appear without traceable evidence.

---

# 7.2 Out of Scope

The following capabilities are intentionally excluded from the MVP.

These are considered future enhancements and are not required to demonstrate the core architecture.

## Continuous Repository Monitoring

Automatic synchronization with repository updates is not included.

Knowledge graph updates are initiated manually.

---

## Multi-Repository Support

The MVP operates on a single application repository.

Cross-service dependency analysis is excluded.

---

## Multi-Application Analysis

The system analyzes one application at a time.

Relationships across multiple products are outside the current scope.

---

## Automatic Test Generation

The system identifies affected areas but does not generate test cases automatically.

---

## CI/CD Integration

Integration with GitHub Actions, Jenkins, GitLab CI, or deployment pipelines is excluded.

---

## Historical Change Analytics

The MVP analyzes individual Pull Requests independently.

Historical trend analysis and release intelligence are deferred.

---

## Learning-Based Relationship Optimization

Relationship confidence is determined using deterministic heuristics and evidence.

The system does not learn edge weights from historical data.

---

## Real-Time Graph Synchronization

The knowledge graph is rebuilt or updated on demand rather than continuously synchronized with application changes.

---

# 7.3 Assumptions

The MVP assumes:

- The target application is publicly accessible.
- The application's source code repository is available.
- Product documentation exists in a machine-readable format.
- The crawler can authenticate only if credentials are explicitly provided.
- The Pull Request contains sufficient contextual information for analysis.
- Source code is parsable by the supported language analyzers.

---

# 7.4 Constraints

The following constraints influenced the MVP design.

- Limited implementation time favors depth over breadth.
- Explainability is prioritized over absolute automation.
- Deterministic processing is preferred wherever feasible.
- Large Language Models are used only where semantic reasoning provides clear value.
- The architecture should remain extensible for future capabilities without major redesign.

# Online Impact Analysis Pipeline

The following functional requirements describe the runtime workflow executed whenever a Pull Request is submitted for analysis. Unlike the Offline Knowledge Construction Pipeline, these components operate on an already constructed Product Knowledge Graph to provide low-latency, explainable impact analysis.

---

# FR-007 — Pull Request Analysis

## Purpose

Analyze incoming Pull Requests and identify the implementation entities modified by the proposed code changes.

## Description

The Pull Request Analyzer shall inspect a Pull Request and extract the set of implementation entities impacted by the proposed changes.

The analysis includes:

- Changed files
- Modified classes
- Added or removed functions
- Updated API endpoints
- Configuration changes
- Dependency modifications

The output of this stage serves as the entry point for graph-based impact analysis.

## Inputs

- Pull Request URL
- Git Diff
- Repository Metadata

## Outputs

- Changed Files
- Changed Code Entities
- Changed APIs
- Modified Dependency Graph

## Acceptance Criteria

- Parse Pull Request successfully.
- Detect added, modified, and deleted entities.
- Map changes to repository entities.
- Ignore formatting-only changes where possible.

## Priority

Critical

---

# FR-008 — Confidence-Aware Graph Retrieval

## Purpose

Retrieve the most relevant portion of the Product Knowledge Graph required for reasoning.

## Description

Rather than reasoning over the entire knowledge graph, the system shall retrieve a focused subgraph centered around the changed implementation entities.

Retrieval shall prioritize relevance using relationship confidence, evidence quality, and graph topology.

## Retrieval Factors

The retrieval process shall consider:

- Relationship Confidence
- Evidence Quality
- Node Importance
- Graph Distance
- Relationship Type

## Outputs

- Relevant Requirements
- Affected Pages
- Connected UI Components
- Related APIs
- User Flow Context

## Acceptance Criteria

- Retrieve only relevant subgraphs.
- Minimize unrelated nodes.
- Preserve complete reasoning paths.
- Support configurable traversal depth.

## Priority

Critical

---

# FR-009 — Reasoning Engine

## Purpose

Infer product-level impact from the retrieved subgraph.

## Description

The Reasoning Engine shall analyze the retrieved graph context to determine the downstream impact of a Pull Request.

The engine shall identify:

- Affected requirements
- Impacted user interfaces
- Potentially broken user journeys
- Regression testing recommendations
- Areas with insufficient evidence

Reasoning shall only occur over the retrieved subgraph.

## Outputs

- Product Findings
- Risk Assessment
- Missing Coverage
- Confidence Scores
- Supporting Evidence

## Acceptance Criteria

- Every conclusion references graph evidence.
- No unsupported inference is generated.
- Ambiguous findings remain explicitly uncertain.
- Reasoning remains reproducible.

## Priority

Critical

---

# FR-010 — Blast Radius Report Generation

## Purpose

Generate an explainable report suitable for engineers, QA teams, and product stakeholders.

## Description

The Report Generator shall transform reasoning results into a structured Blast Radius Report.

The report shall prioritize readability over implementation details.

## Report Sections

The generated report shall include:

- Executive Summary
- Overall Risk Score
- Changed Components
- Affected Requirements
- Affected Pages
- Affected User Flows
- Supporting Evidence
- Confidence Scores
- Regression Recommendations
- Manual Review Suggestions

## Outputs

- Markdown Report
- HTML Report (Optional)
- JSON Representation

## Acceptance Criteria

- Reports generated successfully.
- Every finding references evidence.
- Confidence displayed clearly.
- Report understandable without source code knowledge.

## Priority

Critical

---

# FR-011 — Human Review Workflow

## Purpose

Ensure uncertain conclusions are reviewed rather than treated as facts.

## Description

The system shall explicitly represent uncertainty throughout the analysis pipeline.

When confidence falls below configurable thresholds, findings shall be surfaced for manual validation.

## Confidence Levels

### High Confidence

- Automatically included in report.

### Medium Confidence

- Included with warning.

### Low Confidence

- Flagged for manual review.

## Acceptance Criteria

- Low-confidence findings clearly identified.
- Supporting evidence displayed.
- Human reviewers can validate or reject mappings.
- Manual decisions can update future graph versions.

## Priority

High

---

# FR-012 — Knowledge Graph Persistence & Updates

## Purpose

Maintain a consistent and queryable Product Knowledge Graph over time.

## Description

The graph shall support incremental updates without requiring complete reconstruction whenever possible.

Existing entities should preserve stable identities while allowing mutable properties to evolve.

The update process shall avoid duplicate nodes and relationships.

## Acceptance Criteria

- Existing entities preserved.
- Duplicate entities prevented.
- Relationships updated incrementally.
- Graph integrity maintained after updates.

## Priority

Medium

# 9. Non-Functional Requirements

The following non-functional requirements define the quality attributes expected from the Blast Radius Analyzer. These requirements influence architectural decisions independently of functional capabilities.

---

# NFR-001 — Performance

## Objective

The system shall provide interactive response times for Pull Request analysis while keeping offline graph construction efficient.

### Requirements

- Pull Request analysis should complete within **30 seconds** for medium-sized repositories.
- Knowledge graph queries should return within **2 seconds** for typical retrieval workloads.
- Graph construction should support incremental updates whenever possible.
- Large Language Models should only process the retrieved subgraph rather than the complete graph.

---

# NFR-002 — Scalability

## Objective

The architecture shall scale independently across knowledge construction and online analysis.

### Requirements

- Support repositories containing thousands of source files.
- Support applications consisting of hundreds of pages.
- Support tens of thousands of graph nodes.
- Graph retrieval performance should remain independent of total graph size where possible.

---

# NFR-003 — Explainability

## Objective

Every system conclusion must be explainable.

### Requirements

Every reported finding shall include:

- Supporting graph path
- Evidence source
- Confidence score
- Reasoning explanation

The system shall never produce conclusions that cannot be traced back to graph evidence.

---

# NFR-004 — Reliability

## Objective

Failures in one subsystem should not invalidate the entire analysis pipeline.

### Requirements

- Partial crawl failures should not terminate graph construction.
- Repository parsing failures should be isolated.
- Missing documentation should be reported gracefully.
- Report generation should continue even when certain mappings cannot be established.

---

# NFR-005 — Extensibility

## Objective

The architecture shall support future capabilities with minimal redesign.

### Requirements

The system shall support future addition of:

- New programming languages
- Additional documentation formats
- Alternative graph databases
- New reasoning models
- Additional graph node types
- Multiple repositories

without requiring significant architectural changes.

---

# NFR-006 — Maintainability

## Objective

Each subsystem should have clearly defined responsibilities.

### Requirements

The architecture shall separate:

- Crawling
- Parsing
- Knowledge Fusion
- Identity Resolution
- Graph Construction
- Retrieval
- Reasoning
- Report Generation

Each module should expose well-defined interfaces and minimize coupling.

---

# NFR-007 — Observability

## Objective

The execution of every pipeline stage should be traceable.

### Requirements

The system shall log:

- Crawl progress
- Parsing statistics
- Graph construction metrics
- Relationship confidence distribution
- Retrieval statistics
- Reasoning decisions
- Report generation status

Failures should include sufficient diagnostic information for debugging.

---

# NFR-008 — Security

## Objective

The system shall safely process external repositories and web applications.

### Requirements

- Credentials shall never be stored in plain text.
- Repository access shall respect authentication boundaries.
- External content shall be treated as untrusted input.
- Secrets shall not be embedded into generated reports.
- Sensitive metadata shall be excluded from graph persistence.

---

# NFR-009 — Determinism

## Objective

Repeated executions over identical inputs should produce consistent outputs.

### Requirements

- Graph construction should be deterministic.
- Identity resolution should produce stable entity identifiers.
- Retrieval should return reproducible subgraphs.
- LLM reasoning should be constrained using structured graph context.
- Any non-deterministic findings should be explicitly reflected in confidence scores.

---

# NFR-010 — Evidence Integrity

## Objective

Every relationship within the Product Knowledge Graph shall be verifiable.

### Requirements

Every edge must maintain:

- Evidence source
- Confidence score
- Originating subsystem
- Last verification timestamp

Relationships without supporting evidence shall never be promoted to verified graph edges.

# 11. Risks & Assumptions

## Assumptions

The following assumptions are made for the MVP.

- The target application is publicly accessible.
- A compatible public source repository is available.
- Product documentation exists in a machine-readable format.
- The application's UI can be explored programmatically.
- Pull Requests contain meaningful implementation changes.
- The repository language is supported by the parser.

---

## Risks

### R-001 — Incomplete Documentation

Product documentation may not accurately reflect the implemented application.

**Mitigation**

Represent uncertainty explicitly through confidence scores and unresolved requirements.

---

### R-002 — Dynamic Web Applications

Some UI elements may only appear after authentication or complex user interactions.

**Mitigation**

Support configurable crawl depth and authenticated crawling.

---

### R-003 — Ambiguous Requirement Mapping

A requirement may correspond to multiple pages or implementation entities.

**Mitigation**

Maintain multiple candidate mappings with evidence and confidence rather than forcing a single relationship.

---

### R-004 — Repository Complexity

Large repositories may contain implementation details unrelated to user-visible behavior.

**Mitigation**

Restrict graph retrieval to semantically relevant implementation entities.

---

### R-005 — LLM Variability

Reasoning models may produce inconsistent outputs.

**Mitigation**

Constrain reasoning using retrieved graph context and deterministic evidence.
