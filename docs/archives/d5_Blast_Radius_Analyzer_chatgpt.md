# 1. Executive Summary

## Objective

The objective of this project is to design and implement an AI-powered Blast Radius Analyzer capable of estimating the downstream impact of source code changes before deployment.

Unlike traditional static dependency analysis, the proposed system combines evidence from multiple sources of truth to understand software changes in the context of the entire product rather than only the codebase.

These evidence sources include:

- Product Requirements Documents (PRDs)
- Technical Documentation
- READMEs
- Wikis
- Source Code
- Pull Requests
- API Definitions
- UI Screens
- User Flows
- Runtime Relationships

The final system constructs an Evidence-backed Product Knowledge Graph that connects product requirements with implementation details and user-facing functionality.

When a Pull Request is submitted, the system traverses this graph to estimate which components are likely to be affected and generates an explainable Blast Radius Report supported by traceable evidence.

---

## Core Philosophy

The project follows five engineering principles.

### 1. Evidence over hallucination

Every conclusion generated by the LLM must be backed by concrete evidence extracted from documentation, code, repository metadata, or graph relationships.

The LLM should never invent dependencies.

---

### 2. Retrieval before reasoning

Reasoning is only performed after retrieving relevant graph nodes and supporting evidence.

The Knowledge Graph acts as long-term memory while the LLM acts as the reasoning engine.

---

### 3. Graph-first architecture

Rather than treating documentation, source code, and UI independently, all project artifacts are represented as interconnected nodes within a unified graph.

This enables multi-hop reasoning across different abstraction levels.

Example:

Requirement

↓

↓

↓

↓

Backend API

↓

Service

↓

↓

### 4. Explainability by design

Every prediction must include:

- confidence score
- supporting evidence
- reasoning chain
- affected artifacts
- uncertainty indicators

The report should resemble an engineering impact analysis rather than a generic AI response.

---

### 5. Modular architecture

Every subsystem should be independently replaceable.

For example:

# 2. Problem Definition

## 2.1 Background

Modern software systems consist of thousands of interconnected artifacts spread across multiple abstraction layers.

A single user-facing feature is rarely implemented within a single file or service. Instead, it emerges from the interaction of numerous components including frontend pages, APIs, backend services, databases, feature flags, configuration files, infrastructure, documentation, and business requirements.

Consequently, even a seemingly small code change may produce unintended consequences across the system.

This phenomenon is commonly referred to as the **Blast Radius** of a change.

Understanding this blast radius before deployment is one of the most difficult problems in modern software engineering.

---

## 2.2 What is a Blast Radius?

For the purposes of this project, the blast radius is defined as:

> **The complete set of software artifacts, user experiences, business requirements, infrastructure components, and downstream dependencies that may be directly or indirectly affected by a proposed source code change.**

Unlike traditional dependency analysis, blast radius estimation extends beyond code-level relationships.

It answers questions such as:

- Which user journeys may break?
- Which APIs could change behavior?
- Which frontend pages are affected?
- Which product requirements are impacted?
- Which documentation becomes outdated?
- Which automated tests should be executed?
- Which engineering teams should review the change?
- What confidence do we have in these predictions?

The goal is not merely to identify dependencies, but to estimate the real-world impact of software evolution.

---

# 2.3 Example

Consider the following Pull Request.

```
Optimize User Authentication Flow
```

Files modified:

```
AuthService.java
JWTValidator.java
SessionManager.java
```

Traditional dependency analysis reports:

- Authentication Module
- Session Module

While technically correct, this provides little actionable information.

An AI-powered blast radius analyzer should instead infer something closer to:

### Functional Impact

Affected Features

- User Login
- Password Reset
- Remember Me
- Two-Factor Authentication
- Session Renewal

Affected User Flows

- Login Journey
- Checkout Authentication
- Profile Access
- Admin Portal

Affected APIs

- POST /login
- POST /refresh-token
- POST /logout

Affected Frontend

- Login Page
- Authentication Modal
- Checkout Screen

Affected Documentation

- Authentication Guide
- API Reference
- Security Documentation

Affected Tests

- Authentication Integration Tests
- Session Tests
- End-to-End Login Tests

Risk

High

Confidence

92%

Supporting Evidence

- AuthService calls JWTValidator
- LoginPage consumes Login API
- PRD links Authentication Requirement to Login Flow
- API specification references modified endpoint
- Existing integration tests cover affected services

This report is significantly more valuable than a simple dependency graph because it connects implementation changes to business functionality.

# 2.5 Core Challenges

Building a reliable blast radius analyzer requires solving several independent but interconnected problems.

## Challenge 1 — Heterogeneous Data Sources

The system must integrate information from:

- PRDs
- Product documentation
- Wikis
- READMEs
- Source code
- Git history
- Pull requests
- UI pages
- APIs
- Runtime metadata

Each source has a different structure, terminology, and level of abstraction.

---

## Challenge 2 — Traceability

There is rarely an explicit mapping between:

Requirement

↓

User Story

↓

UI Component

↓

API

↓

Service

↓

Database

↓

Source File

↓

Inferring these relationships is one of the central challenges of the project.

---

## Challenge 3 — Incomplete Information

Real-world repositories often contain:

- outdated documentation
- missing PRDs
- undocumented APIs
- inconsistent naming
- dead code
- legacy modules

The system must remain useful despite incomplete evidence.

---

## Challenge 4 — Explainability

Engineering teams rarely trust AI systems that provide unsupported conclusions.

Every prediction should therefore include:

- evidence
- reasoning
- confidence
- graph path
- source references

Explainability is a first-class requirement rather than an optional feature.

---

## Challenge 5 — Scalability

Enterprise repositories may contain:

- millions of lines of code
- thousands of APIs
- hundreds of services
- years of commit history
- hundreds of thousands of graph nodes

The architecture must support incremental updates rather than rebuilding the entire graph after every commit.

# 3.8 Architectural Implications

The assignment strongly suggests an architecture built around structured knowledge rather than isolated LLM reasoning.

From the requirements analysis, several design implications emerge:

1. A knowledge graph is essential to connect heterogeneous artifacts.
2. Static code analysis alone is insufficient because it lacks business context.
3. Vector search alone is insufficient because it cannot model explicit relationships.
4. LLM reasoning must be grounded in retrieved evidence to minimize hallucinations.
5. Every subsystem should contribute structured entities and relationships to a unified graph.

These implications form the foundation for the technology evaluation chapters that follow.
