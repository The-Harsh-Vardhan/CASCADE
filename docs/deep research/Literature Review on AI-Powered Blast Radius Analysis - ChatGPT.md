# Literature Review on AI-Powered Blast Radius Analysis

We surveyed key research (2015–2026) across the 23 topic areas listed.  Each **relevant paper** is summarized with its bibliographic details and key content, and we note how it could inform our system’s components.  (Citations are given to validated sources for claims.)

## Change Impact Analysis  
- **Kretsou et al. (2021)** – *Change Impact Analysis: A Systematic Mapping Study*. **Authors:** M. Kretsou, E.-M. Arvanitou, et al. Published in J. Syst. Softw. (2021). DOI:10.1016/j.jss.2020.110892. **PDF:** (ScienceDirect) – no free PDF. **ArXiv/GitHub:** n/a. **Citations:** ~50. **Area:** CIA (survey). **Problem:** Understand the state of CIA research and metrics. **Core Idea:** Mapped 111 papers on CIA, categorizing methods and quantified factors (instability, change-proneness, amount of change, changeability). **Architecture:** Systematic literature review. **Algorithms/Models:** N/A. **Data:** Academic papers (2010–2020). **Evaluation:** Qualitative mapping; identified over- and under-studied areas. **Strengths:** Broad coverage; distilled core metrics (e.g. instability). **Weaknesses:** No empirical evaluation on actual code, only literature analysis. **Limitations:** Focused on academic studies, may omit industrial practices. **Relevance:** Provides context for CIA concepts (metrics, benefits) useful for our Requirements and Impact components. **Action:** *Read* – adopt its insights on CIA metrics and practical benefits, adapt by integrating those metrics into our blast radius scoring.

- **Abdurhman & Lee (2023)** – *FCP2Vec: Deep Learning-Based Approach to Software Change Prediction…* Appl. Sci. 13(11):6453 (2023). **PDF:** [MDPI](https://doi.org/10.3390/app13116453). **ArXiv:** n/a. **GitHub:** n/a. **Citations:** ~6. **Area:** CIA via co-change. **Problem:** Predict which files co-change (impact scope) in large code. **Core Idea:** Treats a changelog as sequences (skip-gram Word2Vec) to embed files (“file commit patterns”), then predicts co-changes via nearest neighbors. **Architecture:** Unsupervised embedding (skip-gram) + kNN. **Algorithms/Models:** Word2Vec (skip-gram), kNN for recommendation. **Data:** 3 open-source projects’ commit logs (Git history for Vuze, Spring, Elasticsearch). **Evaluation:** Hit Ratio@K (recall of co-changed files). Achieves ~21% better recall than traditional dependency networks. **Strengths:** Scales to large codebases, learns from history automatically. **Weaknesses:** Requires rich historical data; only file-level (not semantic). **Limitations:** Evaluated on Java projects only; may not capture semantics of changes. **Relevance:** Useful for our Repository Analysis / Impact component (predicting affected code from PR). **Action:** *Adapt* – use its embedding idea for recommending potentially affected components from commit diffs.

## Requirements Traceability  
- **Wang et al. (2024)** – *An empirical study on SOTA methods for requirements-to-code traceability link recovery*. J. King Saud Univ. Comp. Info. Sci., 36(6):102118 (2024). **DOI:**10.1016/j.jksuci.2024.102118. **PDF:** (Open access via ScienceDirect). **Citations:** 0. **Area:** Traceability (requirements-code). **Problem:** Lack of a benchmark comparing RC traceability methods. **Core Idea:** Systematic literature review (2018–2023) of methods for linking requirements to code, with an experimental replication on 13 datasets. **Architecture:** Review+empirical evaluation framework. **Algorithms:** Evaluated 6 SOTA methods (mostly IR-based and ML-based). **Models:** IR (CRT, TAROT, Fine-grained TLR, POS+IR), ML (Random Forest). **Data:** 13 standard traceability datasets (COEST, large industrial ones). **Evaluation:** Replicated methods, measured precision/recall. Findings: CRT, TAROT, FTLR work well on medium data; ConPos and TAROT good on large sets; RandomForest strong across the board. **Strengths:** First comparative benchmark in RC-TLR, open resources provided. **Weaknesses:** Only covers methods up to 2023; evaluation limited to preset datasets. **Limitations:** Focused on IR and basic ML, not neural methods. **Relevance:** Guides linking PRDs to code (our requirement linking component). **Action:** *Read* – adapt insights on effective traceability features (TF-IDF, POS, etc.) and consider implementing TAROT or RandomForest as part of our link recovery.

## Code Property Graphs (CPG)  
- **Saimbhi (2025)** – *Enhancing Software Vulnerability Detection Using CPGs and CNNs*. In ICCCIT 2025. **Author:** A. S. Saimbhi. **DOI:**10.1109/ICCCIT62592.2025.10928033. **ArXiv:** 2503.18175. **PDF:** [arXiv](https://doi.org/10.48550/arXiv.2503.18175). **Citations:** 0. **Area:** CPG / static analysis. **Problem:** Improve vulnerability detection beyond traditional static analysis. **Core Idea:** Builds Code Property Graphs (AST+CFG+DDG) for functions, and feeds them to CNNs specialized for graph data. **Architecture:** (1) Transform code→CPG; (2) Train CNN on CPG data. **Algorithms/Models:** Graph-based convolutional neural networks (GCNN). **Data:** Newly created dataset of functions labeled by vulnerability type (from open-source). **Evaluation:** Accuracy on function-level vulnerability detection tasks (ICCCIT paper format suggests ROC or accuracy, but details not in abstract). **Strengths:** Bridges graph modeling of code and deep learning. **Weaknesses:** Likely high computational cost; single author preprint (not community-validated). **Limitations:** Focuses only on security vulnerabilities, not general CIA. **Relevance:** Technique could be adapted for analyzing code graph structure in impact analysis (Repository Analysis). **Action:** *Consider* – investigate using CPG + GNN for structural code similarity or risk scoring (if applicable to our backend component).  

## Graph-based Software Engineering / Ontologies / Knowledge Construction  
- **RepoDoc: Xu et al. (2026)** – *RepoDoc: A Knowledge Graph-Based Framework to Automatic Documentation Generation and Incremental Updates*. *ArXiv* 2604.26523v1 (29 Apr 2026). **Authors:** D. Xu, M. Liu, X. Wang, J. Zhong, Z. Zheng. **DOI:** (ArXiv 2604.26523). **PDF:** [ArXiv](https://arxiv.org/abs/2604.26523). **GitHub:** [SYSUSELab/RepoDoc](https://github.com/SYSUSELab/RepoDoc). **Citations:** 0 (new). **Area:** Knowledge graphs / documentation (multi-topic: Knowledge Graph, Retrieval, Reasoning). **Problem:** Automated, up-to-date documentation at repository scale. **Core Idea:** Constructs a **Repository Knowledge Graph (RepoKG)** of code entities/relations; clusters modules; uses agent-based LLM queries to generate modular documentation; and propagates changes via graph traversal. **Architecture:** Three-phase pipeline + incremental update: (1) **KG Construction** from AST (entities and relations); (2) **Module Clustering** by graph-based functional cohesion; (3) **LLM Agent Generation** using graph queries (retrieving only relevant code). Plus **Semantic Impact Propagation** for updates. **Algorithms/Models:** AST parsing, graph clustering, topological sort (for update consistency), LLM (DeepSeek V3.2) as generator agents. **Data:** 24 diverse repos (Python, JS/TS, Java, C#, C/C++, PHP) in evaluation. **Evaluation:** Compared against doc baselines (RepoAgent, CodeWiki). Metrics: documentation **coverage** (APIs documented), completeness, time/token usage. RepoDoc improved coverage by 32.5% and completeness by 10.4%, with 3× faster generation and 85% fewer tokens; incremental updates 73% faster, 77% fewer tokens, 10.2% higher recall. **Strengths:** Combines static analysis (RepoKG) with LLMs for structured doc generation; addresses incremental updates explicitly. **Weaknesses:** Depends on LLM backend; metrics specific to docs, not directly to code behavior. **Limitations:** Early-stage (ArXiv), but code is available. **Relevance:** **Crucial** – demonstrates how a knowledge graph can underlie both understanding code/UI and generating text (report generation and documentation). Its impact propagation can inspire our Reasoning component. **Action:** *Adopt/Extend* – adopt the RepoKG concept for linking code modules and adopt its impact propagation algorithms for our Blast Radius report. Use its GitHub tools if possible.

- **Han et al. (2025)** – *Retrieval-Augmented Generation with Graphs (GraphRAG)*. *ArXiv* 2501.00309v2 (Jan 2025). **Authors:** H. Han, Y. Wang, H. Shomer, et al. **DOI:** 10.48550/arXiv.2501.00309. **PDF:** [ArXiv](https://arxiv.org/abs/2501.00309). **GitHub:** [GraphRAG repo](https://github.com/Graph-RAG/GraphRAG). **Citations:** 0 (new). **Area:** Graph retrieval + RAG. **Problem:** Integrating graph-structured data as the knowledge source in RAG frameworks. **Core Idea:** Surveys and proposes a **GraphRAG** framework: defines components (retriever, organizer, generator) specialized for graph data. Reviews GraphRAG for multiple graph types (text, knowledge, social, planning graphs). **Architecture:** Conceptual (survey): query processor → graph retriever → organizer → generator. **Algorithms/Models:** Discusses graph embedding (GraphSAGE, GNN), query planning, LLM integration; no single model. **Data:** Domains: Infrastructure graphs, scene graphs, etc. **Evaluation:** None (survey). **Strengths:** Comprehensive overview of how to combine KGs/graph DBs with LLM retrieval, including multi-hop reasoning. **Weaknesses:** No empirical results (conceptual survey). **Limitations:** Very new; primarily high-level. **Relevance:** Provides the theory of using a **Knowledge Graph as a retrieval source for an LLM (i.e. GraphRAG)**. This directly inspires using the Product KG to feed context to LLM for explanation. **Action:** *Read* – adopt its components (Retriever, Organizer, Generator) design for our Graph Retrieval and Report Generation. Adapt its insights on graph-based retrieval to query our KG effectively.

- **Lewis et al. (2020)** – *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*. NeurIPS 2020. **Authors:** P. Lewis, E. Perez, et al. **DOI:**10.48550/arXiv.2005.11401. **PDF:** [ArXiv](https://arxiv.org/abs/2005.11401) / [NeurIPS](https://papers.nips.cc/paper/2020/hash/9671512a5befcf305f4e0b735974b262-Abstract.html). **Citations:** ~2000 (high-impact). **Area:** RAG (text-based). **Problem:** LLMs lack up-to-date or precise world knowledge; hallucinate. **Core Idea:** Introduces *RAG* models that combine a seq2seq LLM (parametric) with a non-parametric memory (external retriever over Wikipedia) for generation. Two variants: retrieve same passages for all tokens vs. per-token retrieval. **Architecture:** Seq2seq Transformer (BART) + Dense Passage Retriever indexing Wikipedia. At generation, retrieve relevant docs to condition LLM. **Algorithms/Models:** BART / DPR. **Data:** Wikipedia + standard QA tasks (Natural Questions, TriviaQA, etc.). **Evaluation:** Achieved SOTA on open-domain QA; found RAG produces more factual, diverse text than pure LLM. **Strengths:** Pioneering RAG approach, open-sourced. **Weaknesses:** Retrieval limited to text corpus; not graph-structured. **Limitations:** Large compute; retrieval latency. **Relevance:** Conceptual foundation for *Retrieval-Augmented Generation*. Suggests how to augment LLM with evidence (in our case, from the product KG). **Action:** *Adapt* – use the idea of retrieving contextual evidence (via knowledge graph) for justifying our blast radius explanations.

## Knowledge Graph Construction / Ontology / Knowledge Fusion / Autonomous Crawling  
- **Peshevski et al. (2025)** – *AI Agent-Driven Framework for Automated Product Knowledge Graph Construction in E-Commerce*. First GOBLIN Workshop on KG Tech (2025). **Authors:** D. Peshevski, R. Stojanov, D. Trajanov. **ArXiv:** 2511.11017 (Nov 2025). **DOI:**10.48550/arXiv.2511.11017. **PDF:** [ArXiv](https://doi.org/10.48550/arXiv.2511.11017). **Citations:** 0. **Area:** Autonomous agents / KG construction. **Problem:** Manually building KGs for product data is slow and schema-bound. **Core Idea:** Uses *LLM-based agents* to fully automate KG construction from unstructured product descriptions (e.g. e-commerce data). Three-agent pipeline: Ontology creation/expansion, ontology refinement, KG population. No predefined schema is needed; agents handle semantics via LLM reasoning. **Architecture:** Multi-agent LLM framework (prompt-based): one agent designs ontology (classes/relations), another refines schema, a third populates KG from text. **Algorithms/Models:** GPT-style LLMs (not specified); agent orchestration. **Data:** Real-world dataset of air conditioner product descriptions. **Evaluation:** Measures coverage (97% of relevant properties captured) and low redundancy. **Strengths:** Scalability, semantic coherence without hard rules, minimal schema overhead. **Weaknesses:** Depends on LLM correctness; domain limited (only products). **Limitations:** Preliminary (workshop), no code public (that we saw). **Relevance:** Shows how autonomous agents (LLMs) can crawl and extract information into a KG (Crawling, KG Construction, Ontology Design). Suggests using LLMs to populate our Product KG from docs. **Action:** *Consider* – apply agent-based KG population to PRDs and UI docs (we may adapt its agent prompts). Treat it as a model to fuse heterogeneous docs into our graph (knowledge fusion).

## Regression Test Selection  
- **Plyusnin et al. (2025)** – *Targeted Test Selection (T-TS) Approach in CI*. *ArXiv* 2509.10279v1 (Sept 2025). **Authors:** P. Plyusnin, A. Antonov, et al. (T-Technologies). **DOI:** (arXiv 2509.10279). **PDF:** [ArXiv](https://arxiv.org/abs/2509.10279). **Citations:** 0. **Area:** Regression Test Selection (RTS). **Problem:** Running full test suites on every CI commit is costly. **Core Idea:** Proposes **Targeted Test Selection (T-TS)** – an ML method that represents a commit as a “bag-of-words” of changed files plus cross-file features, avoiding heavy coverage maps. Deployed in industry. **Architecture:** ML pipeline: feature extraction (file changes, code analysis), train classifier to predict which tests to run. **Algorithms:** Gradient boosting (likely, or other classifier – not detailed in abstract). **Models:** ML classifier (internally proprietary). **Data:** Both open-source and large private repositories. **Evaluation:** In production CI: T-TS ran only ~15% of tests, cut test time by ~85%, and still detected >95% of failures. **Strengths:** Highly practical; significant savings in a real system. **Weaknesses:** Proprietary (full details not published), unknown generality. **Limitations:** Specific to the T-TS implementation (not open). **Relevance:** Demonstrates ML-based change impact on testing (a form of blast radius analysis for tests). It shows the feasibility of predicting affected components (tests here). **Action:** *Adapt* – use its data representation idea (commit as changed-file tokens) for modeling blast impact. If available, consider contacting authors for more details; otherwise use as inspiration for our impact scoring.

## Summary of Papers by Component
We group the above (and related) works by architecture component:

- **Crawling / Data Collection:** Peshevski (2025) shows AI agents for **autonomous crawling and KG population** from product pages. (Also Wu’s HITL survey implies combining human web queries.)
- **Documentation Parsing:** RepoDoc (Xu et al.) provides **RepoKG construction from code** and LLM-based documentation generation, which parallels parsing PRDs into KG.
- **Repository Analysis:** Romero (2026) and FCP2Vec (Abdurhman 2023) apply LMs and embeddings on repo artifacts to find patterns (commit/bug prediction).
- **Knowledge Fusion / Ontology:** Peshevski (2025) and Zou (2021) address **KG construction/fusion** – Peshevski merges product data via agents; Zou builds a code-centric KG for project data.
- **Identity Resolution:** (No direct paper found. Standard ER techniques from data science might be used to merge duplicated artifacts in the KG.)
- **Knowledge Graph:** RepoDoc, Zou, Wang (2023), Peshevski all describe building software KGs.
- **Graph Retrieval:** Han (2025) details the **GraphRAG** framework, teaching how to retrieve from KGs; Lewis (2020) provides the baseline RAG.
- **Reasoning:** Aleti (2026) and Arora (2025) highlight *trust and explainability* issues in AI (ensuring reasoning is auditable). GUI Agents (Tang 2025) cover *planning* in interface tasks.
- **Report Generation:** RepoDoc uses LLM agents to generate and update documentation; Arora (2025) emphasizes producing explainable decisions (which our report must do).

## Research Gaps

Our search highlights several gaps for this architecture:

- **Integrated Semantic Linking:** No existing system fully connects **requirements, UI flows, and source code** in a unified knowledge graph for impact analysis. Most works focus on one or two artifact types (e.g. code→code, code→req, or code documentation). Our *evidence-backed product KG* addresses this gap directly.
- **Explainable Change Analysis:** Few works generate human-readable explanations of change impact. Most CIA/RAG works produce raw predictions without structured justification. We must innovate by combining XAI and GraphRAG for **explainability** in the blast radius report.
- **LLM-Aided Static Analysis:** While surveys note LLMs in static analysis, concrete systems for LLM-assisted CIA are scarce. We can pioneer by leveraging LLMs (as in RepoDoc and RAG) to reason about graph-structured code changes.
- **Continuous Update / Incremental Learning:** RepoDoc’s incremental doc updating is novel; similar techniques for live CI (dynamic PR analysis) are lacking. Our architecture’s focus on “continual crawling/monitoring” is addressing an open problem.
- **Human-in-the-Loop Interfaces:** Few tools allow developers to guide or correct automated impact analysis. Integrating human feedback loops (as HITL research suggests) remains unexplored in CIA.
- **Unified Ontology:** There is no standard ontology for software artifacts linking UI components, requirements, and code. Building or adopting an appropriate ontology (inspired by Peshevski’s and Zou’s models) is an open challenge.
